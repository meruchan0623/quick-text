# 性能基线与记录（B-53）

状态：骨架，2026-10-22。所有数值栏都是「待实测」，没有任何一个数字是测出来的。预算来自开发计划 §11「性能预算」；测量方法里来自计划的写【计划】，我的建议写【建议】，建议不是已经定下的方案，实施时可以改。

## 1. 用途与规则

1. **基线先行**：0.4 第一周先在 0.3.1 上测出能测的项（钩子耗时、匹配耗时、启动时间、内存、空闲 CPU），填进本文第 3 节的「0.3.1 基线」栏，然后才改性能相关代码。
2. **没有基线，就不写「提升了多少」**。某项基线栏是「待实测」或「不可测」时，发布说明和提交说明里不得对这一项写提升、变快、变省之类的结论；只能写「达到预算」或「未达预算」，且必须附上记录编号。
3. **只按绝对预算判定**。CI 中 criterion 结果超过预算的 120% 时失败；趋势数据作为 artifact 保存，供人工查看。基线用来说明变化，不用来放宽预算。
4. **每条记录都要能复现**：写明环境（第 2 节）、被测构建的提交与配置、冷启动还是预热、样本数、统计口径。缺这些的数据不入表。
5. **口径**：
   - 计时一律用单调时钟（`Instant`、`QueryPerformanceCounter`），不用墙钟。
   - 延迟类指标给 p50、p95，钩子与匹配类给 p99；样本数不足 100 时只给范围，不给 p99。
   - 主进程与 WebView2 分开计：后端指标只统计 `quicker-text.exe`；WebView2 的 browser、renderer、GPU 等子进程单独采样、单独判定，不并入主进程预算。
   - 用 release 配置的构建测量。debug 构建的数据不入表。
   - 同一台机器上，同一指标至少测 3 次，记录最大与最小，别只留最好的一次。

### 3.3 外部采样的做法（【建议】）

- 计数器：`Get-Counter '\Process(quicker-text)\% Processor Time','\Process(quicker-text)\Private Bytes','\Process(quicker-text)\Handle Count','\Process(quicker-text)\Thread Count' -SampleInterval 5 -MaxSamples 60`。`% Processor Time` 是按核累加的值，需除以逻辑核数再与预算比较，记录里写明做了哪一种换算。
- 唤醒次数：Windows Performance Recorder 抓取 CPU 与上下文切换，Windows Performance Analyzer 里按线程统计每秒被唤醒次数；没有 WPR 时用 Process Explorer 的「上下文切换增量」近似，并在记录里标注这是近似。
- 这些采样程序本身会干扰输入测量，输入延迟类指标不要与采样同时测。
- 以上是读取系统计数器和性能追踪，不涉及向目标程序注入输入；需要注入输入的测量（触发到开始输出）在专用测试窗口里按验收模式进行，不在日常使用的窗口里做。

## 4. 浸泡测试记录（B-53）

- 0.4：2 小时，在 L4 环境中运行。1.0（S-27）：24 小时，L4 环境加一台日常使用的实机，并包含睡眠唤醒、锁屏解锁各一次。
