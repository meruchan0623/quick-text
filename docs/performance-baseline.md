# 性能基线与记录（B-53）

状态：骨架，2026-10-22；2026-10-23 补充匹配基准。除第 3.1 节「匹配（1000 条规则）」一行的「0.4.0 实测」栏是本机测量（非 CI，见第 3.4 节）外，所有数值栏都是「待实测」，没有其他任何一个数字是测出来的。预算来自开发计划 §11「性能预算」；测量方法里来自计划的写【计划】，我的建议写【建议】，建议不是已经定下的方案，实施时可以改。

## 1. 用途与规则

1. **基线先行**：0.4 第一周先在 0.3.1 上测出能测的项（钩子耗时、匹配耗时、启动时间、内存、空闲 CPU），填进本文第 3 节的「0.3.1 基线」栏，然后才改性能相关代码。
2. **没有基线，就不写「提升了多少」**。某项基线栏是「待实测」或「不可测」时，发布说明和提交说明里不得对这一项写提升、变快、变省之类的结论；只能写「达到预算」或「未达预算」，且必须附上记录编号。
3. **只按绝对预算判定**。CI 中 criterion 结果超过预算的 120% 时失败；趋势数据作为 artifact 保存，供人工查看。基线用来说明变化，不用来放宽预算。
4. **每条记录都要能复现**：写明环境（第 2 节）、被测构建的提交与配置、冷启动还是预热、样本数、统计口径。缺这些的数据不入表。
5. **口径**：
   - 计时一律用单调时钟（`Instant`、`QueryPerformanceCounter`），不用墙钟。
   - 延迟类指标给 p50、p95，钩子与匹配类给 p99；样本数不足 100 时只给范围，不给 p99。
   - 主进程与 WebView2 分开计：后端指标只统计 `quicker-text.exe`；WebView2 的 browser、renderer、GPU 等子进程单独采样、单独判定，不并入主进程预算。
   - 用 release 配置的构建测量。debug 构建的数据不入表。
   - 同一台机器上，同一指标至少测 3 次，记录最大与最小，别只留最好的一次。

### 3.3 外部采样的做法（【建议】）

- 计数器：`Get-Counter '\Process(quicker-text)\% Processor Time','\Process(quicker-text)\Private Bytes','\Process(quicker-text)\Handle Count','\Process(quicker-text)\Thread Count' -SampleInterval 5 -MaxSamples 60`。`% Processor Time` 是按核累加的值，需除以逻辑核数再与预算比较，记录里写明做了哪一种换算。
- 唤醒次数：Windows Performance Recorder 抓取 CPU 与上下文切换，Windows Performance Analyzer 里按线程统计每秒被唤醒次数；没有 WPR 时用 Process Explorer 的「上下文切换增量」近似，并在记录里标注这是近似。
- 这些采样程序本身会干扰输入测量，输入延迟类指标不要与采样同时测。
- 以上是读取系统计数器和性能追踪，不涉及向目标程序注入输入；需要注入输入的测量（触发到开始输出）在专用测试窗口里按验收模式进行，不在日常使用的窗口里做。

### 3.4 匹配基准（B-53）

运行：`cargo bench -p quicker-domain --bench matching`（`--` 后面不加过滤，判定要求 7 个用例齐全），然后 `pwsh -NoProfile -File scripts/check-bench-budget.ps1`。纯计算，只调用 `quicker-domain`，不注入输入，不装钩子。判定脚本的自测：`pwsh -NoProfile -File scripts/check-bench-budget.ps1 -SelfTest`，只用临时目录里的合成结果，不跑基准。

- **数据**：固定种子生成的合成数据，每次运行、每台机器都相同，不读文件、时钟或环境。1000 条规则分成 40 组，每组 25 条共享一个 3–5 个字母的前缀：
  - 60% 是终止键模式的字面量；
  - 20% 是立即触发的字面量，其中一半是另一半去掉前导符号（`;` `/` `` ` `` `,`）后的触发词，所以每次立即命中都有两个候选参与排序；
  - 10% 是终止键模式的正则；
  - 10% 是忽略大小写、带单独终止键设置的字面量；
  - 另外每第 7 条规则忽略大小写；全局黑名单有 5 个进程。
- **一次迭代等于一次按键**，调用方式与 `crates/platform/src/windows/rawinput.rs` 的 `match_buffer` 相同：
  - 终止键（空格、`;`）先用按键前的缓冲区试终止键规则，没有命中再用包含按键的缓冲区试立即触发规则；
  - 其他字符只试立即触发规则；
  - 缓冲区保留最后 1024 个字符。
- **用例**（组名 `match_1000_rules`）：
  - `char_miss`：普通字符，不命中；
  - `char_immediate_hit`：立即触发词的最后一个字符；
  - `terminator_miss`：普通单词后的空格，两次调用都不命中，这是最常见的终止键按键；
  - `terminator_hit`：字面量触发词后的空格；
  - `terminator_regex_hit`：正则触发词后的空格；
  - `terminator_miss_full_buffer`：缓冲区已满 1024 个字符时的不命中；
  - `typing_stream`：逐键打一段夹有触发词的文字，循环进行。

  判定脚本内置这 7 个用例名（`$ExpectedBenches`）。增加、删除或改名用例时，`matching.rs` 和脚本要一起改，否则判定直接退出 2。

  每个用例测量前先断言是否命中、哪条规则胜出，所以匹配逻辑的改动不会让「命中」用例悄悄变成「不命中」用例。
- **统计口径（近似 p99）**：
  - criterion 不记录单次迭代。它的每个样本是连续 `iters` 次迭代的总时间，写在 `target/criterion/match_1000_rules/<用例>/new/sample.json` 里。
  - 基准使用 `SamplingMode::Flat`，每个样本的迭代次数相同。每个用例取 200 个样本，预热 2 s，测量 6 s。
  - 样本均值 = 样本总时间 ÷ 迭代次数，即这个样本里平均每次按键的耗时。
  - 脚本取 200 个样本均值的最近秩第 99 百分位：升序排列后取第 ⌈0.99 × n⌉ 个。n = 200 时是第 198 个，即倒数第 3 个。
  - 这是「样本均值的 p99」，不是「单次按键的 p99」。偶发的慢按键会被同一样本里的其他迭代摊薄，所以真实的单键 p99 可能更高。反过来，调度抖动影响的是整个样本而不是一次按键，所以它比单键 p99 稳定。
  - 每个单一用例都只重复同一个按键，摊薄作用很小。`typing_stream` 的样本混合了便宜的字符键和昂贵的终止键，不能代表最慢的按键。看最慢的按键要看单一用例，尤其是 `terminator_miss` 和 `terminator_miss_full_buffer`。
  - 样本数少于 100 时脚本直接失败，不给 p99（第 1 节规则 5）。
- **判定**：任一用例的上述 p99 超过 1.2 ms（预算 1 ms 的 120%，第 1 节规则 3）即失败。不与上一次结果比较。
- **只判定完整、同一次运行的结果**（Codex 复审 2）。以下情况脚本退出 2，不给结论：
  - 缺任何一个用例，并列出缺了哪些。例如只跑 `-- char_miss` 时，不能只凭最便宜的用例通过；
  - 结果目录里有清单之外的用例：可能是改名后留下的旧目录，也可能是新增用例忘了加进清单；
  - 7 份 `new/sample.json` 的写入时间相差超过 `-MaxRunMinutes`（默认 20 分钟；完整跑一次约 1–2 分钟），说明有用例的结果是以前某次运行留下的；
  - 给了 `-NotBefore` 时，有结果早于这个时间。
- **CI `bench` 任务的配置**：
  - 先跑判定脚本的自测；
  - 再删除 `target/criterion/match_1000_rules`，因为缓存或上一次尝试可能留下结果；记下开始时间 `BENCH_STARTED`；
  - 不加过滤运行基准，然后以 `-NotBefore $env:BENCH_STARTED` 判定；
  - 运行时机：windows-latest，每晚 02:41 UTC、推送 main 时、手动触发；
  - 产物：运行基准和脚本后，上传 `target/criterion` 作为 artifact（保留 90 天），供人工看趋势；
  - 不在 PR 上运行，不是必需检查。

- 0.4：2 小时，在 L4 环境中运行。1.0（S-27）：24 小时，L4 环境加一台日常使用的实机，并包含睡眠唤醒、锁屏解锁各一次。
- 负载：约每秒 5 个字符的随机文本，夹杂触发缩写；每 10 分钟切换一次目标控件、暂停并恢复一次、写入一段新的剪贴板内容。
- 采样：记录 Private Bytes、句柄数、GDI / USER 对象数、线程数、Health 状态、日志中的 error 条数。监视脚本是 `scripts/soak/soak.ps1`，用法见 `scripts/soak/README.md`。它默认每 10 秒采样一次（`-IntervalSeconds`），输出 `soak.csv`（进程采样）、`events.csv`（日志事件）和 `summary.txt`（汇总）。脚本只采样进程信息、统计日志事件，本身不产生输入。上面的负载要人工打字或用实体按键工具输入；外部模拟输入不能代表实体键盘路径，用它跑的结果不算浸泡通过（README「前提」）。
- 通过标准：没有静默失效（每次触发在历史中都有记录，要么成功，要么是带原因的失败，并与测试窗口的证据一致）；句柄数和线程数不单调增长；结束时 Health 为「正常」；1.0 另要求内存增长 < 20MB。展开成功率门槛（如 ≥ 99.9%）为【推断】，以 0.4 第一次浸泡的结果为依据再定。
